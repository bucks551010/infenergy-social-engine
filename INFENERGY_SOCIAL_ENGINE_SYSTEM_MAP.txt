1. EXECUTIVE SYSTEM DEFINITION
[CONFIRMED] This is a Python social-content generation and publishing service for Infenergy Power. social_engine/start.py imports worker and calls worker.main(). worker.py owns a ThreadingHTTPServer, three daily UTC schedule jobs, manual control endpoints, Meta token refresh, and a process-wide RUN_LOCK. A slot run launches scripts/run_engine.py in a subprocess. run_engine.py loads channel/funnel state, asks scripts/generate_posts.py for content, enforces validation/quality/duplicate/readiness gates, resolves media, calls independent WordPress/Facebook/Instagram/LinkedIn adapters, and writes operational history.
[CONFIRMED] Generation is dual-stack. The default legacy stack is the large generate_posts.py pipeline. The newer scripts/social/orchestrator.py stack can be selected explicitly, by environment, or in best_of mode. The orchestrator is enriched by scripts/business_intelligence when enabled. Both stacks use deterministic decision engines; selected tasks call Gemini and fall back when calls fail.
[CONFIRMED] This is not a queue-based distributed multi-agent system. It is a rule engine plus optional LLM calls, declarative agent contracts, individually dispatchable utility agents, file/SQLite persistence, and synchronous external publishers.

7. DEPLOYMENT ARCHITECTURE
[CONFIRMED] railway.json uses NIXPACKS, startCommand "python social_engine/start.py", restartPolicy ON_FAILURE, max retries 5. requirements.txt drives Python dependency installation. The process exposes PORT (default 8080).
[INFERRED] Persistence across Railway deploys requires DATA_DIR to point to a mounted volume. Code supports DATA_DIR but railway.json does not declare a volume; volume attachment is external platform configuration and cannot be proven from repository files.
Flow: repository -> Railway build -> pip dependencies -> start.py -> worker process -> HTTP thread + scheduler loop -> per-run Python subprocess.

8. SCHEDULER AND TRIGGER SYSTEM
[CONFIRMED] worker.main clears schedule and registers schedule.every().day.at() for morning, midday, evening. Defaults: 13:00, 17:00, 23:00 UTC. POST_SCHEDULE_* overrides them. Comments map defaults to 8am/noon/6pm Central but DST conversion is not dynamic.
[CONFIRMED] Main loop calls schedule.run_pending every 30 seconds. Jobs are memory-only; process restart loses missed jobs; no catch-up/misfire persistence exists.
[CONFIRMED] Scheduled jobs call run_slot synchronously in the scheduler thread. Manual jobs use daemon threads via _start_slot_thread. RUN_LOCK permits one active run; _start_slot_thread returns false when locked.
[CONFIRMED] RUN_ON_STARTUP starts a morning daemon run. Manual overrides become temporary environment values and are restored in finally. Subprocess timeout defaults to 420 seconds.
Trigger map: UTC time or /run-now -> run_slot -> Meta/visual bootstrap -> run_engine subprocess -> generation/publishing.

13. BUSINESS DATA FLOW
Founder manifesto + latest marketing strategy + source registry + owner assertions + catalog facts -> brand/audience/offering builders -> BusinessProfile -> current_profile.json/current_profile.md/version snapshot -> compilers -> orchestrator context/prompts. Overrides are applied only during profile save. API reads persisted current profile first and only assembles if absent, so persisted profile can be stale. 14. PRODUCT/OFFERING DATA FLOW
WooCommerce CSV fields actually read: ID, Name, SKU, Published, Short description, Description, Categories, Regular price, Sale price, In stock?, Stock, External URL, Images. HTML is stripped; numeric metrics are regex-extracted; image URLs are scored/deduped; local images/category fallbacks can supplement. Published rows become product dicts and SQLite products rows.
BI offerings independently parse CSV and merge data/product_briefs by SKU/product id/parent fallback. Used offering fields include id/SKU/name/category/description, price/sale, stock, images, verified_facts, functional benefits, problems addressed, forbidden claims.
Selection uses product id override, category/topic fit, stage preference, recent product history and content bucket. AI copy receives offering identity, benefits/problems, verified facts and forbidden claims in orchestrator; legacy prompts receive product/talking-point summaries. Visuals receive product name, metrics, image candidates/source and visual plan. CTA/destination uses product_url where available, otherwise site URL. Publishers consume captions, URL, generated visual/product image.
Ignored/weak fields: many raw CSV columns are never read; raw long descriptions are reduced to snippets/metrics. If BI offering cannot match catalog, URL/stock/price can be empty. SQLite upsert does not establish deletion of products absent from later CSVs.

17. CONTENT GENERATION SYSTEM
Request -> stage/channel context -> editorial bucket (no_product/product_education/conversion proportions) -> product/topic -> strategic brief -> optional phase 2 ideation/psychographic/narrative/voice/hook prompts -> optional phase 3 precision/compliance/novelty prompts -> phase 4 visual/CTA prompts -> fallback/model caption -> platform adaptation -> visual plan/image -> control metadata -> final dict. 22. INFORMATION EACH AGENT ATTEMPTS TO DETERMINE
Strategist: what persuasion strategy/persona/awareness/emotion/law/CTA fits. Has product/stage/history; lacks independently verified customer research.
Editorial/topic engines: what should be discussed now. Have queue/graph/history/product; external timeliness only via RSS agent.
Copy calls: how to express approved strategy. Have brand/product/audience/claim boundaries; derive words and beats; do not discover facts.
Visual calls: what scene/layout communicates copy and then pixels. Have product images/style/copy; may hallucinate visual text/product form, hence QA.
Claim/quality modules: whether output is supported, useful, non-repetitive and aligned. Have configured facts/history/rules; lack legal adjudication.
Engagement/performance/learning agents: what performed and what reusable signal follows. Have metrics only if platform ids/credentials/history metrics exist; current history has none.
Conference: whether declared roles have their required inputs. It derives readiness, not marketing content.

65. ARCHITECTURAL RISKS/WEAKNESSES
One 4,600+ line generator and a large run engine mix ownership. Multiple product/brand/history truths can drift. Current history shape is incompatible with rich run-engine expectations. Persisted BI profile is preferred over fresh assembly and can stale. Environment is global mutable process state, though RUN_LOCK mitigates slot overlap. AI calls are split across wrappers, weakening uniform retry/cost/prompt audit. Broad exception fallbacks can hide quality degradation. Query-string admin secrets can leak. Meta tokens are plaintext on disk. Scheduler/missed jobs and retries are not durable. Generated assets/artifacts grow without cleanup. Platform list is hard-coded across modules. External model names age. Configuration duplication/migration obscures effective source. Preview is not strictly side-effect-free. Tests mock external services, so passing tests do not establish live credentials/provider availability.

71. IF I KNEW NOTHING ABOUT THIS SOFTWARE, EXPLAIN EXACTLY HOW THE WHOLE THING WORKS
Railway starts a small Python bootstrap, which starts worker.py. The worker opens an HTTP server and keeps three daily timers. A timer or protected manual URL starts one slot, but a lock prevents two slots at once. The worker refreshes visual settings and, when needed, Meta credentials, then launches the actual run engine in a separate Python process.

The run engine reads schedules, funnel goals, recent history and enabled channels. It asks the generator for one content package. The generator knows the brand from manifesto/profile files, products from WooCommerce CSV/SQLite/BI offerings and product briefs, audiences/topics from configuration and BI, and prior creative from history files. Deterministic logic chooses a stage, audience, topic, product, persuasion structure, emotion, hook and CTA.

Depending on configuration, the old generator creates the post, the new Social Intelligence Orchestrator creates it, or both compete. AI is not in charge of the whole system. Gemini is asked bounded questions such as how to write structured beats, propose visual concepts, refine creative roles, generate an image, or review that image. Facts and forbidden claims are inserted into prompts. If Gemini is absent or fails, templates/rules take over. The conference called "agents" mostly describes data contracts; individually dispatched agents are utility functions, and they do not converse autonomously.

The result becomes WordPress, Facebook, Instagram and LinkedIn-specific text plus platform images. The run engine checks claims, brand rules, quality, repetition, channel readiness and media. A rejected candidate can be regenerated or recorded as skipped. An accepted candidate is published sequentially through each platform's API adapter. One platform error does not prevent later platforms from being attempted. Results should be saved to history and the worker updates status.

The system remembers posts, topics, hooks and visual signatures in JSON, keeps products/brand/visual settings in SQLite, and versions BI profiles/evidence/overrides on disk. It has agents and files capable of collecting engagement and writing learning signals. However, no always-on feedback loop automatically fetches every platform's performance, learns, rebuilds the profile and changes the next post. Humans still supply business truth, catalog exports, legal claim decisions, credentials, configuration, overrides and the choice to run live. The system is highly automated and selectively AI-assisted; it is not fully autonomous.

AUTONOMY: automatic selection/generation/gating within human-provided boundaries; no durable autonomous operations/learning loop.
AGENTICITY: orchestrated modules and callable agents, not an independent multi-agent organization.
LEARNING LOOP: substrate exists; closed loop does not.

INCOMPLETE: unified telemetry/prompt registry, durable jobs/retries/approval, analytics ingestion across channels, automatic learning, retention.
